# 錄影失敗處理規則（P1／P3）

每條規則都說明五件事：
- 怎麼偵測；
- 系統自動做什麼；
- 小老師看到什麼；
- 總覽顯示什麼；
- 通知誰、P1 怎麼紀錄。

表中的時間都是預設值，**待 Justine 決定**。程式依據見 [`p1-p3-handoff-spec.md`](p1-p3-handoff-spec.md)；合成測試對照見 [`p3-mvp-acceptance.md`](p3-mvp-acceptance.md)。

## 共同原則

- 只有 Zoom 確認，才算「錄影中」「已停止」「錄影已完成」。
- 只有 P1 確認，才算「已歸檔」。
- 推測一律標示「推測」。
- 任何檢查失敗都視為「不可以」：不發入場憑證、不錄影、不上傳。
- 課程本身盡量照常進行，總覽只負責觀察，沒有任何控制功能。
- 所有自動動作都有固定的鍵，重複執行不會重複動作。每一步都寫成事件，可以稽核。

## 1. 錄影啟動失敗

| 情況 | 系統動作 | 總覽 | 通知、紀錄 |
|---|---|---|---|
| API 回錯誤 | 最多試 3 次，間隔 10 秒、30 秒 | 「已送出錄影啟動請求（重試中）」 | — |
| 3 次都失敗 | 不再自動重試；課程照常進行；小老師畫面提供「請管理員協助」。不改用本機錄影 | 「錄影失敗」，列為異常 `RECORDING_FAILED` | 通知管理員；這堂課沒有錄影檔 |
| 收到 202，但 60 秒內沒有確認 | 向 API 核對 | 「已送出錄影啟動請求」，資料狀態「延遲」 | — |
| 收到 202，但 2 分鐘內沒有確認 | 再送一次 start | 「錄影失敗（推測）」，異常 `START_UNCONFIRMED` | 通知管理員 |
| 確認晚到 | 改回錄影中 | 「錄影中（延遲確認）」 | — |
| Zoom 雲端空間已滿，或沒有 Storage Plan | 同「API 回錯誤」；錯誤代碼待實測 | 「錄影失敗」 | 通知管理員檢查方案 |

## 2. 入場與中途加入

| 情況 | 系統動作 | 總覽 |
|---|---|---|
| 身分不明、不在名單上、不在入場時間內 | **入場前就擋下**：不發入場憑證，回 403 和原因代碼 | 「有人入場被擋」，只顯示次數 |
| 家長沒有同意錄影的學生 | **照常上課**，整堂課不錄影；在開始錄影之前就決定好，不會錄到一半再暫停 | 「不錄影（同意條件不符）」 |
| 名單上、已同意的學生晚到 | 不影響錄影 | 「在線，遲到」 |
| 已入場者斷線後重連 | 重新跑一次入場檢查，再簽發新的 30 分鐘憑證 | 「重新連線中」→「在線」 |
| 教室出現沒有入場紀錄的 `user_key` | 主持人端把對方移出；正在錄影就啟動第 3 節的停止程序；對方加入之後錄到的檔案一律 `HOLD` | 異常「出現身分不明的參與者」 |

## 3. 上課途中撤回同意

| 時間點 | 系統動作 | 總覽 |
|---|---|---|
| 撤回當下 | 同時送出兩道停止指令：REST `recording.stop`，以及主持人端的 `stopCloudRecording()` | 「錄影中（已送出停止請求）」，提醒「課中撤回錄影同意」 |
| 30 秒內沒有確認 | 再送一次停止指令 | 同上，資料狀態「延遲」 |
| 60 秒內仍沒有確認 | 伺服器結束 session，師生重新進入不錄影的新 session | 「可能已停止（推測）」，直到 Zoom 確認 |
| 要求結束後 60 秒仍無法確認 | 標記 `WITHDRAWAL_STOP_UNCONFIRMED` 為錯誤，立即通知管理員，持續核對 | 異常「撤回同意後仍無法確認錄影已停止」 |
| 錄影檔 | 內容超過撤回時間的檔案 `HOLD`，絕不上傳；全部在撤回之前的檔案隔離到 `_待確認` | 「已隔離或暫緩，待管理員處理」 |

這堂課接下來的時間都不會再錄影。撤回之前錄到的內容要保留還是刪除，**待 Justine 決定**。

## 4. 突然斷線

| 情況 | 偵測 | 系統動作 | 總覽 |
|---|---|---|---|
| 學生斷線 | SDK 的 `isInFailover`（官方：2 分鐘後移除）；webhook 的 `leave_reason` | 不影響錄影 | 「重新連線中」→「已離開（斷線）」 |
| 小老師斷線，2 分鐘內回來 | 心跳中斷，加上 SDK 的 `Reconnecting` | 重連時重新跑入場檢查；錄影是否持續以 Zoom 回報為準 | 「重新連線中」或「可能離線（推測）」→「在線」 |
| 小老師**直接關機** | 心跳超過 60 秒沒有回報；Zoom 仍列出小老師時，提醒「小老師端訊號中斷」 | 向 API 核對 | 「可能離線（推測）」，資料狀態「延遲」 |
| 小老師確認離開 | Zoom 大約 2 分鐘後送出 `user_left`（斷線） | 離開滿 5 分鐘停止錄影，滿 15 分鐘結束 session；回來就停止計時 | 「已離開（斷線）」→ 已停止 → 已結束 |
| 全員離開或全員斷線 | 最後一位離開時 session 結束（官方說明）；Zoom 還沒確認前標示「推測」 | 核對結束時間，接著等錄影檔 | 「已結束（推測）」→「已結束」；錄影「可能已停止（推測）」→「錄影已完成」 |
| 網路時好時壞 | 每次中斷和恢復都會記錄 | 錄影以 Zoom 回報為準；若被分成多段，命名為 P01、P02 | 顯示「連線品質不穩」提醒 |

主持人離開或直接關機時，錄影會不會繼續、主持人身分會不會轉移，官方文件都沒有寫，**待實測**（RT-3、RT-4）。

## 5. 錄影完成通知延遲或遺失

| 情況 | 系統動作 | 總覽 |
|---|---|---|
| 錄影停止或 session 結束 | 開始等錄影檔 | 「已停止，等待錄影檔」，或「可能已停止（推測）」 |
| 30 分鐘還沒收到 | 向 `GET /recordings` 核對，之後每 30 分鐘一次 | 提醒「錄影檔逾時未到」，資料狀態「延遲」 |
| 6 小時還沒收到 | 升為錯誤並通知管理員；繼續核對 | 異常 |
| 通知晚到，或靠核對找到 | 和 webhook 用同一套去重規則，只歸檔一次 | 「錄影已完成」→「已歸檔」 |
| 下載 token（24 小時）過期 | 用 API 重新取得下載網址 | — |

檔案在 Drive 核對無誤之前，Zoom 上的副本**絕不刪除**。等待的門檻要用實測的處理時間來校正（RT-6）。

## 6. Webhook 與我方伺服器

| 情況 | 系統動作 |
|---|---|
| 資料庫出錯或逾時 | 回 503，Zoom 會在 5 分鐘、再 20 分鐘、再 60 分鐘後重送；去重鍵確保不會重複 |
| 簽章錯誤或時間戳過期 | 回 401，不寫入，Zoom 也不重送。連續失敗就通知管理員，檢查 secret 是否被換掉或設定錯誤；漏掉的事件靠核對補回 |
| 端點驗證失敗（每 72 小時一次） | 連續失敗 6 次，Zoom 會停用訂閱，所以第 2 次失敗就要通知管理員 |
| 我方伺服器整個中斷 | 課程照常進行，因為影音不經過我們。恢復後，用 `type=past` 查出當天所有課程補齊，錄影檔照常歸檔 |
| 小老師端的回報寫不進去 | 心跳本來就會持續送來，不需要補 |
| worker 當機 | 租約到期後，工作會由下一個 worker 接手；歸檔具冪等性，見規格第 7 節 |

## 7. 歸檔

| 情況 | 系統動作 | 總覽 |
|---|---|---|
| Drive 上傳失敗，或容量不足 | 依退避時間重試：30 秒起，每次加倍，最長 30 分鐘；沿用 P1 的容量警示 | 「歸檔中」 |
| 試 5 次仍失敗 | 標記 `FAILED`，通知管理員，Zoom 上的副本保留 | 「歸檔失敗」 |
| 上傳成功後、寫入資料庫前當機 | 重試時用 `appProperties` 找到已上傳的檔案，直接採用 | 「已歸檔」 |
| 兩個 worker 搶同一筆工作 | 防護號擋下舊 worker；多出的副本移到垃圾桶 | 「已歸檔」，只有一份 |
| 不在排課表上的 session 錄影 | `HOLD`，不上傳，通知管理員 | — |

## 8. 未經核准的錄影

| 情況 | 系統動作 | 總覽 |
|---|---|---|
| 帳號層級的 Automatic recording 被誤開，或主持人自行開始錄影 | 標記 `UNAPPROVED_RECORDING_START`。這堂課如果不能錄，就走停止保護程序，錄到的檔案 `NO_CONSENT`、`HOLD`；如果可以錄，只通知管理員 | 異常「出現未經核准的錄影」 |

預防方式：Zoom 帳號必須關閉 Automatic recording，以及兩個「參與者可開始或要求錄影」的設定。取得授權後要實測確認（RT-1）。

## 9. 其他

| 情況 | 處理 |
|---|---|
| 總覽頁故障 | 不影響上課或錄影，因為總覽唯讀 |
| 時鐘誤差 | 同一堂課的事件依 Zoom 的時間排序；逾時以伺服器時間計算；比對時允許 2 分鐘誤差 |
| 課程超時 | 表定下課 15 分鐘後仍未結束，提醒「超過表定時間仍未結束」；不強制結束 |
| 錄影後家長才撤回同意 | 沿用 P1 規則：隔離，依保存政策處理（待 Justine 決定） |
