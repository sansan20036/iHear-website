# 管理員即時教室總覽（Live Classroom Dashboard）

需求來源：Justine 老師問「如果同時有幾堂一對一課程上課，能不能從網站後台看到活動？」，這項功能已正式納入 P3 MVP。

本文件是設計規格。規則已用合成原型驗證，相關程式和測試見文末；網站本身尚未修改。

## 1. 八項需求與對應設計

| # | 需求 | 對應設計 |
|---|---|---|
| 1 | 每堂一對一課程使用獨立教室，可以多堂同時上課 | 每堂課開一個 Zoom session（`session_key` = `lessonId`）。每個事件只影響自己那一堂。合成測試確認：同一堂課單獨跑，或和其他 9 堂一起跑，結果完全相同 |
| 2 | 顯示進行中、等待開始、已結束和異常的課程 | 分成四組，見第 2 節 |
| 3 | 每間教室顯示課程代碼、開始時間、小老師與學生到課、錄影狀態 | 卡片欄位，見第 2 節 |
| 4 | 分清「已送出錄影啟動請求」「錄影中」「錄影失敗」「錄影已完成」 | 只有 Zoom 確認了，才算錄影中。202 只代表已送出請求，見第 3 節 |
| 5 | 用 Zoom 事件加上持久化狀態；webhook 延遲或遺失時要能重新核對 | 先寫入事件紀錄，再由事件推導狀態；另有狀態重新核對，見第 4、5 節 |
| 6 | 只有授權管理員能看，不公開個資、下載網址或憑證 | 只開放網站 owner，只顯示代碼，見第 6 節 |
| 7 | 巡堂列為後續功能，先完成權限與資料模型設計 | MVP 不提供巡堂，也沒有影像牆，見第 7 節 |
| 8 | 評估 2、5、10 堂同時上課 | 見第 8 節 |

## 2. 畫面

### 2.1 四個分組

| 分組 | 條件 |
|---|---|
| 進行中 | Zoom 已確認開始，而且還沒結束 |
| 等待開始 | 還沒收到任何開課的確認 |
| 已結束 | Zoom 確認結束；或者所有人都已離開（此時標「推測」，等 Zoom 確認） |
| 異常 | 有錯誤等級的異常，不論上課狀態。卡片上仍會顯示它原本的狀態 |

### 2.2 每張教室卡片

| 欄位 | 內容 |
|---|---|
| 課程代碼 | 例如 `TEST-L001` |
| 開始時間 | 表定時間，以及實際開始時間 |
| 小老師、學生 | 只顯示代碼，加上到課狀態：未到、在線、重新連線中、可能離線（推測）、已離開（附原因：斷線、自行離開、課程結束、被移出），遲到時另外標示 |
| 錄影 | 見第 3 節 |
| 歸檔 | 歸檔中、已歸檔、已隔離或暫緩（待管理員處理）、歸檔失敗 |
| 資料狀態 | 即時、延遲、異常，並附上最後一次確認的時間 |
| 異常與提醒 | 見第 3.3 節 |

## 3. 狀態與依據

### 3.1 每項事實都附上依據

| 依據 | 來源 | 畫面上的寫法 |
|---|---|---|
| 已確認 | 簽章正確的 webhook、REST API 查詢結果、主持人端的 Video SDK | 直接寫出狀態 |
| 已請求 | 我們已經送出指令，還在等 Zoom 確認 | 例如「已送出錄影啟動請求」「錄影中（已送出停止請求）」 |
| 推測 | 由逾時或訊號中斷推算出來 | 一律加上「（推測）」 |

**鐵則：**「錄影中」「已停止」「錄影已完成」「已歸檔」只能來自確認。合成測試會檢查 10 堂課在 60 個時間點的全部 600 張卡片，確認沒有任何推測被顯示成確認。

### 3.2 錄影狀態

| 狀態 | 畫面文字 | 依據 |
|---|---|---|
| `NOT_REQUESTED` | 未開始 | — |
| `BLOCKED` | 不錄影（同意條件不符） | 我方的決定；課程照常進行 |
| `START_REQUESTED` | 已送出錄影啟動請求；API 回錯誤時加註「（重試中）」 | 已請求 |
| `RECORDING` | 錄影中；webhook 晚到時加註「（延遲確認）」 | 已確認（附上確認的來源） |
| `PAUSED` | 暫停 | 已確認 |
| `STOPPED` | 已停止，等待錄影檔 | 已確認 |
| `POSSIBLY_STOPPED` | 可能已停止（推測） | session 已結束，但 Zoom 沒有送來停止的通知 |
| `FAILED` | 錄影失敗：API 連續回錯 3 次時是已確認；收到 202 但 2 分鐘內沒有確認時是推測 | 已確認或推測 |
| `COMPLETED` | 錄影已完成 | `recording_completed`，或從 API 查到全部檔案都已處理完成 |

歸檔狀態另外顯示，例如「已歸檔」只能來自 P1 的 `p1.filing STORED`。

### 3.3 資料狀態與異常

**資料狀態：**
- **即時：** 進行中的課程在 90 秒內有新的確認，而且畫面上沒有推測。
- **延遲：** 符合下列任一情況時：
  - 超過 90 秒沒有任何確認；
  - 畫面上有推測；
  - 「已請求」超過 60 秒還沒有確認；
  - 出現檔案逾時、資料過時、小老師端訊號中斷這三種提醒之一。
- **異常：** 有錯誤等級的異常。

**異常代碼**（門檻都是預設值，待 Justine 決定）：

| 代碼 | 等級 | 條件 | 畫面文字 |
|---|---|---|---|
| `TUTOR_ABSENT` | 錯誤 | 開課 10 分鐘後小老師還沒到 | 小老師未到 |
| `STUDENT_ABSENT` | 提醒 | 開課 10 分鐘後學生還沒到 | 學生未到 |
| `START_UNCONFIRMED` | 錯誤 | 收到 202，但 2 分鐘內沒有確認 | 錄影啟動未獲 Zoom 確認 |
| `RECORDING_FAILED` | 錯誤 | API 連續回錯 3 次 | 錄影啟動失敗 |
| `RECORDING_STOPPED_UNEXPECTEDLY` | 錯誤 | 上課中錄影停止，但我們沒有要求停止 | 錄影意外停止 |
| `UNAPPROVED_RECORDING_START` | 錯誤 | 出現我們沒有核准的錄影（自動錄影誤開、主持人自行開始，或不能錄的課程被錄了） | 出現未經核准的錄影 |
| `CONSENT_WITHDRAWN` | 提醒 | 上課途中撤回同意 | 課中撤回錄影同意 |
| `WITHDRAWAL_STOP_UNCONFIRMED` | 錯誤 | 要求結束 session 已經 60 秒，仍無法確認錄影停止 | 撤回同意後仍無法確認錄影已停止 |
| `FILE_OVERDUE` | 30 分鐘時是提醒，6 小時後升為錯誤 | 錄影已停止，但檔案還沒到 | 錄影檔逾時未到 |
| `FILING_FAILED` | 錯誤 | 歸檔試 5 次仍失敗 | 歸檔失敗 |
| `UNKNOWN_PARTICIPANT` | 錯誤 | 教室裡出現沒有入場紀錄的 `user_key` | 出現身分不明的參與者 |
| `STALE_DATA` | 提醒 | 進行中，但 5 分鐘沒有任何確認 | 資料可能過時 |
| `HOST_SIGNAL_LOST` | 提醒 | 小老師端超過 60 秒沒有心跳，但 Zoom 仍列出小老師（斷線後 Zoom 大約保留 2 分鐘） | 小老師端訊號中斷 |
| `QUALITY_ALERT` | 提醒 | 10 分鐘內收到 `session.alert` | 連線品質不穩 |
| `OVERRUN` | 提醒 | 表定下課 15 分鐘後仍未結束 | 超過表定時間仍未結束 |
| `JOIN_BLOCKED` | 提醒 | 有人入場被擋 | 有人入場被擋（只顯示次數） |

## 4. 事件與持久化

| 來源 | 特性 | 用途 |
|---|---|---|
| Zoom webhook（簽章正確） | 可信，但可能延遲（論壇回報從幾分鐘到 30 分鐘以上）、遺失、重複或亂序 | 開課與下課、進出、錄影的開始、暫停、繼續、停止與完成、連線品質 |
| Zoom REST 查詢 | 可信，但只代表查詢當下 | 重新核對：session、名單、錄影檔 |
| 主持人端 SDK（小老師的瀏覽器） | 即時，但屬於自我回報，所以會標示來源 | 心跳、錄影狀態、他人進出、連線變化（`Reconnecting`、`isInFailover`） |
| 我方伺服器 | 我們自己的動作 | 資格判斷、送出的請求與 API 的回應、停止與結束、通知 |
| P1 | 歸檔結果 | `STORED`、`QUARANTINED`、`HOLD`、`FAILED` |

**事件紀錄：**
- 所有事件都先寫入只增不改的 `classroom_events`，靠語意去重鍵避免重複。
- 心跳例外：每堂課只保留最新的一筆。

**狀態推導：** 每堂課的狀態，是用「這堂課的事件」加上「現在時間」算出來的純函式。
- 同一組事件不論以什麼順序抵達，算出的狀態都一樣。合成測試用 50 種順序驗證過。
- 重送的事件也不會改變結果。
- `classroom_state` 只是快取，隨時都能重新算出來。

## 5. 狀態重新核對（webhook 延遲或遺失時）

**什麼時候觸發：**
- 收到任何 webhook；
- 小老師端送來心跳（每 30 秒一次，錄影中每 10 秒一次）；
- 總覽頁輪詢（每 15 秒一次，分頁隱藏時暫停）；
- 每分鐘的排程：Vercel Pro 才能每分鐘執行；Hobby 最多一天一次，只能當作每日的安全網；
- 管理員按「重新核對」。

**哪些情況要核對**（每堂課每分鐘最多一次，最急的先做）：

| 原因 | 條件 | 優先順序 |
|---|---|---|
| `stop_unconfirmed` | 撤回同意後，停止還沒獲得確認 | 0 |
| `start_unconfirmed` | 已送出啟動請求超過 60 秒 | 1 |
| `host_signal_lost` | 小老師端心跳中斷 | 1 |
| `end_unconfirmed` | 所有人都離開了，但 Zoom 沒有確認 session 結束 | 2 |
| `stale` | 進行中，但 5 分鐘沒有確認 | 2 |
| `overrun` | 表定下課 15 分鐘後仍未結束 | 3 |
| `file_overdue` | 錄影已停止 30 分鐘還沒收到檔案；之後每 30 分鐘一次，最多到 6 小時 | 4 |
| `filing_overdue` | 錄影已完成 1 小時，還沒歸檔 | 5 |

**呼叫的 API 與用量：**
- 每次核對要呼叫兩支 HEAVY API（session 詳情和名單），以及一支 LIGHT API（錄影檔）。
- 預算是每分鐘最多 20 次 HEAVY，也就是最多 10 堂課。
- 官方給 Build 帳號的限額比照 Pro：HEAVY 每秒 10 次，HEAVY 和 RESOURCE-INTENSIVE 合計每天 30,000 次。合成模擬中 10 堂課同時上課時，每分鐘最多用到 4 次。
- 查詢結果先去除姓名、IP、裝置等個資，再寫成 `zoom_api` 事件，所以和 webhook 送來的同一件事會被去重。
- 如果 API 也查不到，就標示「資料可能過時」，不自行猜測。

## 6. 權限與資料保護

**誰能看：**
- 重用 P2 的 `auth()` 和 `resolveAdminPrincipal()`（`lib/admins.ts`）。
- 沒有登入回 401。登入了但不是 owner 回 403，editor 也一樣。MVP 只開放 owner。
- 之後若要開放給其他人，再另外新增 `classroom.dashboard.view` 權限。

**回應：**
- 一律加上 `Cache-Control: private, no-store` 和 `Vercel-CDN-Cache-Control: no-store`，和現有的 `/api/admin/me` 一致。

**卡片內容：**
- 卡片由推導出的狀態逐欄組成，**不轉送任何原始事件**。
- 學生和小老師都只顯示代碼。小老師要不要改顯示姓名，待 Justine 決定。
- 絕不出現：姓名、email、電話、Zoom 顯示名稱、IP、裝置、下載網址、下載 token、JWT、各種金鑰。
- 合成測試把這些字串故意植入模擬的 Zoom 資料裡，確認它們不會出現在資料庫、Drive 或總覽中。

**總覽唯讀：** 只有「重新核對」一個按鈕，沒有開始或停止錄影的功能。

## 7. 巡堂（後續候選，這一輪只完成設計）

**權限與開關：**
- 另外設一個 `classroom.observe` 權限，預設不給任何人。
- 功能開關預設關閉。
- MVP 沒有巡堂按鈕，也**不做同時顯示所有教室影像的影像牆**。

**資料模型：**
- `lesson_participants.role = observer`。
- `observer_visits` 記錄誰、哪堂課、原因、進出時間，並寫入稽核紀錄。

**規則**（之後啟用時）：
- 入場憑證用 `role_type` 0，`user_key` 以 `obs-` 開頭。
- 小老師和學生畫面上會看到「管理員巡堂中」。
- 巡堂者不算到課，也不列入學生的錄影同意判斷。
- 巡堂者會被錄進合併影片，所以必須事先告知工作人員。巡堂者的鏡頭和麥克風預設關閉，待 Justine 決定。
- 費用：每巡一堂，就多一位參與者的分鐘數。

## 8. 2 堂、5 堂、10 堂同時上課的評估

一對一課程，每間教室 2 人，以下都以「同時上課 1 小時」計算。

| | 2 堂 | 5 堂 | 10 堂 | 依據 |
|---|---|---|---|---|
| 參與者分鐘 | 240 | 600 | 1,200 | 計算 |
| 錄影分鐘 | 120 | 300 | 600 | 計算 |
| **Video SDK**：同時開的 session 數 | 不限 | 不限 | 不限 | 官方：可以同時進行不限數量的 session |
| **Video SDK**：能同時錄幾場 | **未記載** | **未記載** | **未記載** | 要向 Zoom 確認，並實測（RT-8） |
| **Video SDK**：使用費（每參與者分鐘約 US$0.0035） | 約 US$0.84 | 約 US$2.10 | 約 US$4.20 | 第三方資料，**未確認**。官方只說「依分鐘用量計費、預付點數」，沒說是按參與者還是按 session 計 |
| **Video SDK**：錄影費（每分鐘 US$0.01–0.015） | 約 US$1.2–1.8 | 約 US$3.0–4.5 | 約 US$6–9 | Zoom 人員 2023 年在論壇的說法，**未確認**；另需 Storage Plan，月費未知 |
| **Zoom Meetings（現有授權）**：需要幾位有授權的主持人 | Pro 2 位／Business 1 位 | 5 位／3 位 | 10 位／5 位 | 轉載的 Zoom 支援文章說：Pro 每位授權主持人一次只能主持 1 場，Business 可主持 2 場（官方原文待確認） |
| **Zoom Meetings**：每多一個授權的費用 | | | | 官方美國牌價：Pro 每人每月 US$14.16（年繳）；經認證的非營利組織 5 折 |
| **Daily（備案）**：使用費（每參與者分鐘 US$0.004） | 約 US$0.96 | 約 US$2.40 | 約 US$4.80 | 官方價目；每月前 10,000 參與者分鐘免費 |
| **Daily（備案）**：錄影費（每分鐘 US$0.01349） | 約 US$1.62 | 約 US$4.05 | 約 US$8.09 | 官方價目 |

**我方系統的負荷：**
- **webhook：** 每堂課大約 10–15 次，最壞情況是重送 3 次。10 堂課每小時最多約 450 次，很少。
- **小老師端心跳：** 錄影中每 10 秒一次。10 堂課大約每秒 1 次小請求，資料庫每堂課只更新一筆。
- **總覽輪詢：** 每位管理員每 15 秒一次。
- **歸檔：**
  - 同時處理 2–3 個檔案，用 resumable 分段上傳，避開 Vercel 函式的時間上限：Hobby 300 秒、Pro 800 秒。
  - 每小時的錄影檔有多大、Drive 容量夠不夠，要實測（RT-6）。
- **Vercel 方案：** 每分鐘核對需要 Vercel Pro。Academy 有收費，本來就可能需要 Pro；Hobby 僅限非商業用途。

**還不知道的事：**
- Zoom 實際能同時錄幾場：這是 2、5、10 堂評估裡最大的未知數。
- 實際費率，以及 Storage Plan 是否非買不可。

以上都要等你授權查看帳號後才能確認，見 [`zoom-account-check.md`](zoom-account-check.md)。**合成模擬通過，不代表實際的並行錄影容量已經驗證。**
